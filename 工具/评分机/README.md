# JYC 评分机 v2

> 说明（2026-11-23）：本文写于比赛期间（2026-10-11 至 10-15）。当时评分机部署在一台私有服务器上（文中的 personal），这个服务已于 2026-10-31 停用，服务器上的数据已清空。代码完整保留，可以按第 5 节自己部署；数据不在仓库里，准备方法见仓库根目录的 `DATA.md`。文中的 `ssh personal`、`remote_score.sh`、`~/jyc_scorer` 是当时的用法和安装目录，换成自己的主机和目录即可。

> **安全提示**：评分机没有任何身份认证，并且会直接执行上传的代码（因子脚本、notebook、SQL、端到端推理代码）。它只能监听本机地址（`127.0.0.1`），或者放在带身份认证的反向代理后面，不能直接暴露在公网或不可信的网络上。

它按比赛平台 `jyc_eval` 的同一流程评分：官方标签，10 个风格加 32 个申万一级行业剔除，同样的五项指标定义。

可以直接上传**平台提交用的文件**：传统因子的 `.ipynb` / `.py`，或端到端三件套 / zip。评分机在模拟平台上原样运行这些代码。网页上能看结果、实时日志、参照池对比和 API 文档。

## 1. 怎么用

### 网页

服务只监听所在机器的 `127.0.0.1:46220`。在同一台机器上直接打开 <http://127.0.0.1:46220>；服务在另一台机器上时，先建 SSH 隧道再打开同一地址：

```bash
ssh -N -L 46220:127.0.0.1:46220 <评分机所在主机>
```

- **提交评分**：把文件拖进页面，类型会自动识别。
- **任务**：实时日志、状态和结果，可以取消。
- **对比**：多个任务的五项指标并排比较。
- **参照池**：已知公榜分数的因子。
- **说明 / API**：完整说明和接口文档。交互式接口文档在 `/docs`。

### 从另一台机器一键提交（不用建隧道）

`remote_score.sh` 通过 SSH 把文件传到评分机所在主机，在那里用 curl 提交。主机别名用环境变量 `JYC_SCORER_HOST` 指定（默认值 `personal` 是比赛期间的别名），安装目录用 `JYC_SCORER_REMOTE_DIR` 指定。

```bash
bash 工具/评分机/remote_score.sh 因子代码/104_同伴残差阶梯过度中性.ipynb -- start=2024-01 end=2024-12
bash 工具/评分机/remote_score.sh e2e/提交/E21_E18g加两个GRU成员_2020-24.zip -- start=2024-01 end=2024-03
bash 工具/评分机/remote_score.sh -- kind=fid fid=104 start=2023-01 end=2024-12
```

脚本等任务完成后，把 `report.md`、`result.json`、`log.txt` 取回本机的 `工具/评分机/结果/<任务号>/`（运行时生成，不在仓库里），并打印报告。

### 评分机所在机器的命令行

```bash
cd ~/jyc_scorer && .venv/bin/python score.py <文件...> --start 2024-01 --end 2024-12
```

### API

例如：

```bash
curl -F files=@x.ipynb 'http://127.0.0.1:46220/api/jobs?wait=true'
```

字段说明见网页的“API”标签。

列表接口分页（2.4.0）：`GET /api/jobs?limit=&offset=&status=&q=&kind=`，总数在响应头 `X-Total-Count`；`GET /api/leaderboard` 加了 `q`、`offset`、`limit`，结果按任务变化缓存。任务状态里的报错信息截断到 2000 字（曾有 KeyError 把整列因子值打进报错，单个任务状态近 10 MB，`limit=300` 的列表一次 70 MB），完整内容在任务日志里。

## 2. 提交类型

| 类型 | 上传 | 运行方式 |
|---|---|---|
| `platform` | 平台用的 `.ipynb` / `.py`，定义 `main(datasources, start_date, end_date)` | 模拟平台：`import dai` 指向本地 DuckDB 0.9.2（与平台同版本），**SQL 原样执行**；跳过含 `jyc_eval` 的自测单元 |
| `e2e` | `Transformer_modelsave_train.py` + `Transformer_modelsave_predict.ipynb` + `transformer_model.json`，或它们的 zip | 运行推理 notebook 的 `main`（CPU torch），不训练 |
| `values` | parquet / csv，三列 `date, instrument, factor` | 真实代码或 `ID0006` 伪代码都可以 |
| `factor_py` | `.py`，定义 `factor(panel)` | `panel` 是 `localeval.build_panel` 的结果加 factor_lib 中间量；按年分块计算，每块预热 6 个月 |
| `fid` | factor_lib 编号 | 同上 |
| `sql` | `.sql`，返回三列 | 可直接引用平台表名 |

模拟平台的数据表：

- `cpt_jyc_2026_stock_bar1m`：单位元，OHLC 缺失为 NULL，含 `pre_close`、`adjust_factor`、`instrument_id`、`instrument`。**本地只有 3 档，4–5 档为 NULL，用到时会提示。**
- `all_instruments`
- `cpt_jyc_2026_instruments`：当日有行情的股票 × 8 个截面
- `cpt_jyc_2026_vwap`：本地重建的标签
- `cpt_jyc_2026_exposure`

`filters` 的语义与平台相同。

平台型提交还会检查输出格式：三列、8 个截面、重复键、inf，以及每个截面相对股票池的缺失率是否超过 40%。任务内存超过 30 GB 或运行超过 3 小时会被终止，和平台限制一致。

已用平台输出核实的两条行为，评分机按同样方式处理：
- **缺失和全 0 不同。** 股票池里没有有限因子值的股票，不论是 NaN 还是缺行，都算缺失；任一截面缺失超过 40%，平台直接报 `v6.datachecker.DataValidationError: 截面因子缺失率不得高于 40%`，不给分。评分机给出同样的报错文字，指标仅供诊断，这类任务也不进赋分表。全 0 能通过检查。
- **常数（含全 0）截面在评测时被跳过**，不计为 IC = 0。平台自测里 104 号的 09:30 全为 0，平台给出 IC 0.0659、IC_IR 1.088；按"跳过"算是 0.0663 / 1.089，按"记为 0"算是 0.0580 / 0.951。

## 3. 返回什么

每个任务输出 `result.json` 和 `report.md`，网页上直接可视化：

- **五项原始指标**，以及不剔除风格时的对照值。
- **分截面明细**：IC、IC_IR、正 IC 比例、因子覆盖、常数或全 0 的截面数（能看出 09:30 缺陷这类问题）。
- **压力和换手**：压力的高低两组、两条腿各自的换手、每截面多空收益的均值和标准差、IC 分位数。
- **分年、分半年**的五项指标。
- **逐日曲线**：IC、20 日均线、累计 IC。
- **配对比较**（`paired`）：与基线比较五项指标。每个因子用**自己实际参与评测的截面**，和平台一致：常数或全 0 截面被跳过，其余截面全部计入。按交易日成块重抽样。
  - 2026-10-12 前的版本只在两边共同的截面上比较。两边对 09:30 的处理不同时，09:30 被漏掉，曾把 09:30 有信号的 181、178 号误判为显著优于 104：旧版 +0.06、z=+3，实际 −0.065、z=−2.6。
  - `POST /api/admin/rescore`（JSON：`ids` / `name_prefix` / `baseline`）用当前评分代码重新评分已完成的任务，不用重算因子值。
  - 输出：指标之差、按 20 个交易日分块的自助法标准误、z 值、日度 IC 相关，以及结论。|z| ≥ 2 视为显著；不足 60 个交易日不做判断。
  - 基线用 `baseline` 指定：已完成的任务号，或 `ref:编号`。默认 `ref:104`。
  - **头部封顶**（2.4.0 起提示）：综合百分位以参照池为总体，104 号已是参照池里 IC_IR 和压力的第一名。候选和基线都在某项的顶端时，这一项的差异不计入综合百分位，`composite.capped_metrics` 列出这些项，结论里也会提示。头部候选请以分项 z 为主。
  - **判断一个候选是否真的比另一个好，看这里，不要看估计公榜分。** 两个相近的因子在同一批截面上评估，共同噪声相互抵消。例如 104 号的变体之间，IC_IR 差的标准误约 0.004–0.01，而单个 IC_IR 的标准误约 0.05。
- **参照池**：有公榜分数的因子，用实际提交到平台的代码在评分机上按平台方式运行后评分（2026-10-11 起）。
  - **公榜估计**（2.5.0）：这个估计模型是用本队自己已提交因子的公榜分数拟合的，在每日提交名额有限的条件下，用来给本地筛选做外部检验；它只用到本队自己的因子和它们的公榜分。锚点 = 参照池里 `calib=true` 的因子，必须是同一时刻抄下的公榜分（现为 2026-10-12 第二十七批同批快照，23 个：A 组 8 个 + 老因子 15 个）。对每个候选取标准化指标空间里最近的 `PUB_KNN`（5）个锚点，估计 = 平均（锚点公榜分 + Σ `PUB_BETA` × 本地指标差）。
    - `PUB_BETA`（config.py）是本地单位下的边际价值，由这 23 个分数拟合：换手、IC 均值本地→公榜几乎 1:1（残差 0.002 / 0.0008），全额计入；IC_IR、压力样本外残差大（0.022 / 0.039），减半；多空夏普秩相关只有 0.59，不计入。
    - 留一法：全体误差 0.0115、秩相关 0.83；头部（≥ 0.75）误差 0.011、**秩相关约 0.05**。它能分档，分不出头部先后。中性化力度这类本地看不见、公榜上却很大的改动（233 → 237：本地 IC_IR +0.004，公榜 +0.041），它同样看不见。
    - 离最近锚点的距离超过锚点彼此最近距离的 90% 分位时标“外推”（`pub_extrap` / `estimate_extrapolated`），例如换手远低于全部锚点；这时线性边际价值不再可靠，百分位会饱和。
    - 旧版（≤ 2.4.3）用“本地综合分 → 公榜分”线性拟合，A 组内部秩相关 −0.1，已替换。
  - 更新快照：编辑 `refs_manifest.json`（每项 `fid / name / public_score / snapshot / calib / job`，`job` 是平台代码在评分机上的已完成任务号；新快照之外的条目把 `calib` 改成 false），然后在容器里 `python refs.py build /app/refs_manifest.json`，再 `POST /api/admin/reload_refs`。任务号不变的因子直接复用序列，一分钟左右完成。
  - 用到 4–5 档盘口的因子本地算不准，不进参照池。
  - 旧版用 factor_lib 的 30 分钟面板复刻，没有平台 SQL 的 09:30 缺陷；88–112 号在平台上 09:30 全为 0，面板版却有信号，所以头部校准失效。
- **相关性**：与 90、104、105、107 号的截面秩相关。
- **赋分表**（网页"赋分表"页，`GET /api/leaderboard`）：
  - 按平台的赋分规则排名：五项指标各自在本表全部因子中的百分位，等权平均，换手越低越好。
  - 总体包括参照池，以及区间覆盖赋分窗口（默认 2023-01 ~ 2024-12）的全部已完成任务；同名任务只保留最新一次。
  - 同时列出各项第一名、帕累托前沿，以及每个因子百分位最低的一项（短板）。
  - 每个任务评分时保存逐截面序列 `series.npz`，赋分表从中切出统一窗口。旧任务用 `python leaderboard.py backfill` 补算。
  - 总体只有我们自己的因子，头部比公榜拥挤，分差会被放大。它用来衡量进步和找短板，不是公榜分的估计。
  - 2.5.0 起另列**公榜估计**（`pub_est`、名次 `pub_rank`、锚点 `pub_anchors`、外推标记 `pub_extrap`），`sort=pub_est` 按它排序；返回体的 `pub_calibration` 给出锚点数、快照和留一法误差。参照池因子在表里只出现一次（作为参照池行，用留一估计），不再和它的来源任务重复。
- **任务管理**：
  - 网页"任务"页可以勾选后批量取消、删除，也可以按名称前缀取消或删除，或一键取消全部排队任务。
  - API：`POST /api/batch/cancel`、`POST /api/batch/delete`，以及 `DELETE /api/jobs/{id}?force=true`。
  - `priority=high` 的任务排在所有普通任务之前。
- **数据合规**（2.4.0）：按 DAI 模拟层实际读到的表（`dai_queries.json`）检查。读了 `cpt_jyc_2026_exposure`（第 t 天的市值、风格按当天收盘计算，`ret` 是当天收益）或 `cpt_jyc_2026_vwap`（标签窗口的 VWAP）的任务，`result.json` 有 `data_violation` 字段，报告和网页置顶标红，不进赋分表。2.4.0 之前的这类任务列在 `store/excluded.json`（任务号 → 原因），赋分表同样跳过；这个文件每次请求都重新读，改了不用重启。
  - **2.5.1 起暴露表解禁**（2026-10-12 用户确认因子赛道可读）：暴露表移出禁用表，读了它的任务只加 `data_notice` 提示（只能用前一交易日及更早的值，是否错位由代码保证，评分机检查不出来）；`cpt_jyc_2026_vwap` 仍是 `data_violation`。`excluded.json` 里错一天的 338–343、349 已移出（备份 `excluded.json.bak-1012-lag`），用当天值的仍然排除。
- **格式与覆盖**：平台规则检查、代码映射、覆盖率、警告。
- **运行信息**：耗时和内存峰值。

## 4. 架构与性能

```
上传 → runner.py（子进程：模拟平台 / 面板 / 文件 → 因子值）→ scoring.py（服务进程内，常驻评分核心）→ result.json / report.md
```

- **评分核心 `engine.py`**：与因子无关的部分预先计算并存在 NVMe 上，用内存映射读取：
  - 评估行（8 个截面）
  - 标签
  - 每个截面 [1, 10 风格, 32 行业] 的正交基 U，用 SVD 取秩，阈值与 `np.linalg.lstsq` 相同

  对每个因子只需三步：
  - 剔除风格：一次矩阵乘法 z − U·Uᵀz；
  - 秩：向量化的组内平均秩；
  - IC、多空、换手、压力：`bincount`、集合求交的向量化实现。

  结果与 `localeval.evaluate` 逐位一致（见验收第 1 项）。分年、半年由逐截面序列切片得到。
- **多核与调度**：
  - 剔除风格用线程池并行（numpy 矩阵乘法释放 GIL）。每个 SQL 的 DuckDB 用 8 线程，端到端推理的 torch 用 12 线程。
  - 平台型任务的大部分时间在因子代码自己的单线程 pandas 上，CPU 不是瓶颈，内存才是：内存够时并发越多吞吐越高，超出后所有任务一起换页、停顿（2026-10-12 实测：5 个整区间任务各占 6–7 GB，容器 35.4/36 GB，PSI full 约 33%）。所以按内存**动态**放行（2.4.1），而不是固定并发数：
    - 每个任务的预留 = 预测峰值：同一 SQL 家族（输入里含 SELECT 的三引号字符串的摘要）、同区间长度、同分块方式的已结束任务峰值的 75% 分位；家族样本不足 3 个时用同类型的；再不足时用 `JYC_KIND_MEM_GB` 的默认值（平台型 5 GB、面板类 6–8 GB、端到端 12 GB）。峰值是短暂的，各任务一般不同时到峰值，超出的风险由下面两项实时检查兜底。（2.4.1 曾用 90% 分位 × 1.1，整段调用时预测 9 GB，只放行 2 个，CPU 只用到约 9%，2.4.2 改回。）
    - 预算 = 容器上限 − 服务进程常驻 − 评分预留（`JYC_SCORE_HEADROOM_GB`，每槽位 3 GB × 评分槽位），且不超过 `JYC_MEM_BUDGET_GB`（28）。运行中任务按 max(预留, 实际 RSS) 计，加上新任务的预留不能超过预算。
    - 容器实际剩余（扣掉运行中任务还没涨到预留的部分）要够新任务的预留；容器内存压力（PSI some avg10）超过 `JYC_MAX_MEM_PRESSURE`（5%）时不放行。
    - 槽位上限 `JYC_MAX_CODE_JOBS`（8）只作兜底：端到端任务占 3 个，values 任务不占，其余各占 1 个。
    - `/api/health` 的 `scheduler` 给出动态预算、内存压力、每个运行中任务的预留和队首任务的预留。
    - 先进先出：队首放不下时，后面的任务不插队，避免大任务饿死。
    - 可用内存取宿主机可用内存与容器 cgroup 剩余（上限 −（用量 − 非活跃页缓存））中的较小者。psutil 在容器里只看得到宿主机的 43 GB，看不到容器 36 GB 的上限；服务进程评分时峰值约 12 GB，不计入预算，所以 2.4.0 起放行前还要看容器的实际剩余。
    - 每次评分、重新评分后调用 `malloc_trim`，把 glibc 堆里的空闲内存还给系统，服务进程的常驻内存不会停在峰值。`/api/health` 的 `memory_gb` 给出容器剩余和服务进程常驻内存。
  - 任务子进程的 `oom_score_adj` 设为 1000，内存吃紧时内核先杀任务子进程，不会杀服务进程。被 OOM 杀掉的任务会排到队首单独重跑一次。
  - 服务重启时，排队中和运行中的任务按提交顺序重新排队，不会丢失。运行中的任务从头再跑。
  - 其他保护：
    - 调度线程遇到异常只记录、不退出，避免队列永久停住。
    - 同步接口线程池放大到 256，大量 `wait=true` 请求同时挂起时 `/api/health` 仍能响应。
    - 评分服务内的秩缓存上限 768 MB（有锁）。服务进程内同时评分 `JYC_SCORE_SLOTS`（2）个任务，一批任务同时完成时不用逐个排队。
    - 同一任务第二次被 OOM 杀掉时直接判失败，并给出明确原因。
  - 线上的并发参数在 Quadlet 的 `Environment=` 里设置。JSON 值的整条赋值必须用单引号包住。容器时区设为 `Asia/Shanghai`，与宿主机一致。
- **评分**：
  - 组内秩改为"值快排 + 组号基数排序"，比两键 lexsort 快约 1.5 倍。
  - 秩按 (行选择, 数值) 的内容摘要缓存：标签、参照因子和候选因子的秩在同一任务的多次调用之间、以及多个任务之间复用。
  - 单次评分（两年平台型任务）31 s → 冷启动约 11–22 s，缓存命中后约 5–11 s。结果与旧版逐位相同。
- **DAI 模拟**（2026-10-12 实测，因子 258，2023-01 ~ 2024-12）：
  - SQL 是提交代码原样执行，不能改写。DuckDB 的耗时主要在逐行的 `strftime`、`CASE` 投影和过滤上，读 parquet 只占约一成。线程数 4 → 8 → 16 时一个季度的查询 55 → 32 → 24 s，所以每个任务的 DuckDB 线程改为 8。
  - 分块方式：按季度调用 `main` 时每次连同回看期重扫约 16 个月，单个任务约 880 s，常驻约 4 GB；整个区间一次调用（`chunk=none`，与平台相同）只扫约 32 个月，单个任务约 390 s，但常驻 7–8 GB。两者结果逐截面秩相关 0.99988（差异来自回看窗口和 EWMA 的预热）。
    - 2.4.0 曾默认整段调用，结果同时运行的 5 个任务占满 36 GB 容器、开始换页（PSI full 约 33%）；2.4.1 按内存限流后只能跑 2 个，CPU 利用率很低。内存是瓶颈时，"每个任务快一倍、内存翻倍"并不划算，而 SQL 缓存又消除了按季度分块重扫的主要代价（同一批任务各季度的 SQL 都命中缓存）。所以 2.4.2 起默认改回按季度，整段调用留给最终确认。
  - **SQL 结果缓存**（2.4.1）：读 1 分钟行情的查询以（SQL 原文、各表文件清单及大小和修改时间、日期与股票过滤、DuckDB 版本）为键，结果 parquet 存在 `store/dai_cache/`（上限 `JYC_DAI_CACHE_GB`，20 GB，按最近使用淘汰）。同一批文本补丁变体大多只改 pandas 部分，最近 147 个平台任务里最常见的 3 种 SQL 覆盖 88 个。同一个键用文件锁互斥：第一个任务执行，其余等它写完直接读，命中后读取约 1 s。含 random、now 等不确定函数的 SQL 不缓存。
    - 结果：命中与写入缓存的那次逐位相同。DuckDB 多线程求和的浮点累加顺序本来就不固定，两次重新执行之间 `SUM` 会差约 1e-14（相对），缓存让同一批任务的输入完全一致。
  - **预取下一块**（2.4.3）：按季度分块时，runner 把当前块和下一块告诉 DAI 模拟层；一条读 1 分钟行情的查询拿到结果后，按"过滤区间相对当前块的偏移"推出下一块的过滤区间，在后台线程里用同一条 SQL 预先算好放进缓存，任务做完 pandas 来取时直接命中。同一个键已有人在算就跳过。实测 258 号两个季度 161 s → 128 s，第二块 SQL 30 s → 0.55 s，因子值完全相同。`JYC_DAI_PREFETCH=0` 关闭。
  - **SQL 线程按并发分配**（2.4.3）：拿到闸门时数一下正在执行的 SQL，线程数 = `JYC_DUCKDB_MAX_THREADS`（22）÷ 正在执行的个数。一批任务步调一致时，每段只有一个 SQL 在跑，用满全部核：27 s → 约 19.5 s。
  - **SQL 并发闸门**：缓存未命中真正执行 SQL 时，同时最多 `JYC_DAI_SQL_SLOTS`（3）个查询，每个 8 线程（跨进程文件锁），避免 6 个任务 × 8 线程抢 24 核（实测同时执行时单个 SQL 160–246 s，单独 66–74 s）。
- **磁盘**：
  - 1 分钟原始 Feather 只在预处理时顺序读一次，可以放在慢盘。
  - 平台格式的 1 分钟 parquet（snappy，按日期排序，每个行组 50 万行，DuckDB 按日期跳过不需要的行组）约 15 GB，放在固态盘。
  - 评分核心约 3.5 GB，按月面板约 4 GB，也放在固态盘。
- **内存**：比赛期间的机器共 42 GB，三处用法如下。
  - 评分核心用内存映射，热数据留在页缓存里。
  - 面板类因子按年分块计算。全量 5 年一次性计算因子 104 时实测超过 34 GB，分块后单块峰值大约是它的五分之一。
  - 参照池按年分块，中间量每块只算一次。
- **GPU**：不使用。评分引擎受内存带宽限制，数据拷进拷出 GPU 的时间比省下的计算还多；端到端推理用 CPU 版 torch。

## 5. 部署与维护（Podman Quadlet）

这一节说明比赛期间的部署方式，照着做可以在自己的机器上运行。下面的 `~/jyc_scorer` 是安装目录的例子。

**先决条件**

- 数据：`data/` 下要有 30 分钟行情（`bar30m/*.feather`）、官方风格暴露（`exposure/`，含伪代码对照表 `id_map.csv`）和官方标签缓存 `labels_y_off.parquet`，另外要有 1 分钟原始 Feather 的目录（环境变量 `JYC_RAW_1M`）。这些数据都不在仓库里，其中风格暴露和对照表不在主办方的公开下载包里。
- 预处理：`python prepare_data.py all` 生成 `store/`（平台格式的 1 分钟 parquet、评分核心、按月面板、参照池）。
- 路径由环境变量 `JYC_DATA`、`JYC_STORE`、`JYC_JOBS`、`JYC_RAW_1M` 指定（见 `config.py`）。`JYC_RAW_1M` 的默认值是比赛期间服务器上的路径，自己部署时必须设置。

**容器**

服务以 rootless Podman 容器运行：
- 定义：`~/.config/containers/systemd/jyc-scorer.container`（仓库里的 `jyc-scorer.container` 是模板，`IMAGE_TAG` 是占位符，挂载路径和资源上限要按自己的机器修改）。
- 镜像：`localhost/jyc-scorer:<版本>-<git短哈希>`，由 `Containerfile` 构建。代码和锁定版本的依赖打包进镜像，torch 用 CPU 版。
- 数据不进镜像：`data/`（只读）、`store/`、`jobs/`、`logs/` 和 1 分钟原始数据（只读），都从宿主机挂载。`UserNS=keep-id` 让容器内进程以宿主机当前用户的身份运行，文件属主不变。
- 网络：只发布在 `127.0.0.1:46220`（`PublishPort=127.0.0.1:46220:46220/tcp`）。容器里的 uvicorn 监听 `0.0.0.0`，对外的范围完全由 `PublishPort` 决定，所以这一行不能改成 `0.0.0.0`，也不能省略地址。**服务没有身份认证，并且会执行上传的代码**：从别的机器访问时用 SSH 隧道，或者放在带身份认证的反向代理后面，不要直接对外开放端口。模板里的 `Network=observability.network` 是比赛期间接入监控用的，自己部署时删掉或换成自己的网络。
- 资源：比赛期间容器上限是 `--memory=36g --cpus=22`（后来调整过，以模板里的 `PodmanArgs` 为准）；每个任务子进程另有 30 GB / 3 小时的看门狗。
- 监控与日志：`/metrics` 提供 Prometheus 格式的指标（任务状态、运行中任务的内存、核心与参照池是否载入），`/api/health` 是健康检查接口，`HealthCmd` 运行 `/app/healthcheck.py`，日志走 journald。

不用容器时，可以在宿主机的虚拟环境里直接运行：`uvicorn server:app --host 127.0.0.1 --port 46220 --workers 1`（用户级 unit 的例子见 `jyc-scorer.service`）。

升级流程（2.4.3 起用 `deploy.sh` 无损升级：先 `POST /api/admin/drain` 排空——不再放行新任务，运行中的跑完，排队的保留——再换镜像重启，重启后排队任务按原顺序继续，没有任务被打断重跑）：

```bash
rsync 代码到 ~/jyc_scorer/build/ && bash ~/jyc_scorer/build/deploy.sh <新标签>
```

手动升级：

```bash
rsync 代码到 ~/jyc_scorer/build/
cd ~/jyc_scorer/build && podman build -t localhost/jyc-scorer:<新标签> -f Containerfile .
# 改 jyc-scorer.container 的 Image=，然后
systemctl --user daemon-reload && systemctl --user restart jyc-scorer
```

宿主机上的虚拟环境（`~/jyc_scorer/.venv`）保留，用于命令行评分（`score.py`）；容器出问题时也可以停掉容器，改用上面“不用容器”的方式运行。

预处理也可以在容器里运行（挂载同上）：

```bash
podman run --rm --userns=keep-id -v ~/jyc_scorer/data:/app/data:ro -v ~/jyc_scorer/store:/app/store \
  -v <1 分钟原始数据目录>:/raw1m:ro localhost/jyc-scorer:<标签> python prepare_data.py all
```

- `localeval.py`、`factor_lib.py` 逐字复制自 `工具/本地评分/`。两者更新后要复制过来，重建镜像，再重跑 `prepare_data.py core --force` 和 `refs --force`。
- `factor_lib.FACTORS` 里的公榜分数更新后，重跑 `prepare_data.py refs --force`。
- 迁移核对（2026-10-11）：同一个任务分别交给宿主机版和容器版，`result.json` 里的指标、明细、参照池、相关性逐位相同；验收结果见第 7 节。

## 6. 与平台的已知差异

## 2.5.2（2026-10-12 准备，10-15 补充）：任务目录归档

- 任务目录增长很快：每个任务约 46 MB，比赛期间每天约增加 23 GB。`archive_jobs.sh` 把结束超过 12 小时的任务（done / failed / cancelled）搬到容量更大的归档盘上的归档目录，原位置留绝对路径符号链接；任务盘剩余空间小于 25 GB 时不看时间、全部搬。由 `jyc-archive.timer`（用户级，每 6 小时）运行。脚本里的源目录和归档目录是比赛期间服务器上的路径，自己用时要改。
- 容器要把归档目录挂到容器里的同一路径，链接在宿主机和容器里才都能解析。
- 删除已归档任务时，`server.py` 先删链接再删归档目录（`shutil.rmtree` 不跟随符号链接，否则静默失败、重启后任务"复活"）。
- `store/dai_cache` 和 `jobs/` 都是可重建或会归档的大目录，如果宿主机对安装目录做定期快照，建议把这两个目录排除在快照之外，否则搬走或删除的数据要等旧快照过期才真正释放空间。
- 2026-10-15：`因子实验/fetch_results.sh`、`score_local.sh` 默认不再下载 `factor_raw.parquet`（取回的结果目录曾因此堆了 24 GB 副本），需要时设 `FETCH_RAW=1`。
