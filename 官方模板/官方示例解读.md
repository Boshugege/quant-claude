# 三份官方示例：它们说明了什么

研究日期：2026-09-26。依据是主办方在比赛平台上提供的三份因子示例脚本（下文按写法称 pandas 版、SQL 版、UDF 版），并对照之前提供的赛事介绍。你随后补充：赛事股票池已从中证 2000 改为**中证 1000**，以获取更多可用于训练的数据。

三份示例脚本是主办方的材料，不随本仓库发布；端到端赛道的官方 Transformer 示例同样不发布。本文只保留我们自己的解读：公式、接口和观察到的差异，不贴示例代码。文中提到的行号指示例原文件的行号。

## 接口约定

两个赛道的提交接口都由官方示例确定，本仓库的全部提交代码都沿用它。

**因子赛道**（要求汇总见 `提交须知.md`）：

- 平台调用 `main(datasources, start_date, end_date)`，一个提交只定义一个 `main`。
- 返回值必须且仅包含 `date`、`instrument`、`factor` 三列；`date` 只能落在 8 个采样点（09:30、10:00、10:30、11:00、11:30、13:30、14:00、14:30），`date + instrument` 不重复。
- 行情表名从 `datasources["bar1m"]` 取，不写死。

**端到端赛道**（说明见 `e2e/README.md` 和 `e2e/submission/README.md`）：三个文件平铺在同一目录上传，文件名固定。

| 文件 | 作用 |
|---|---|
| `Transformer_modelsave_train.py` | 训练脚本和全部共享定义。私榜阶段平台调用其中的 `train_and_save` 从零重训 |
| `Transformer_modelsave_predict.ipynb` | 推理 notebook，只加载权重打分，不训练。平台调用其中的 `main(datasources, start_date, end_date)`，返回同样的三列 |
| `transformer_model.json` | 模型权重和推理配置，文本格式（JSON），不超过 50 MB |

推理 notebook 从训练脚本导入定义，所以训练脚本的文件名不能改。

## 三份示例是同一个因子的三种实现

| 示例（原文件名） | 谁来计算 | 怎么读 |
|---|---|---|
| pandas 版（`demo_py.py`） | DAI 读取原始数据，pandas/NumPy 在 Python 中计算 | 最适合先读懂公式与流程；数据量大时会占用较多本地/Notebook 内存 |
| SQL 版（`demo_sql.py`） | DAI 引擎执行 SQL，在查询端完成加权、分段与聚合 | 适合后续在官方平台处理大规模分钟数据；实际速度需实测 |
| UDF 版（`demo_udf.py`） | Python 定义两个函数，通过 DAI UDF 在查询中调用 | 适合表达 SQL 不方便写的计算；注册和执行能力需按平台/SDK 分别验证 |

它们不是三个独立因子，也不是训练模型或完整交易策略。流程是：**取盘口 → 每分钟算一个数 → 半小时平均 → 按该截面的股票池筛选 → 返回三列 → 在官方平台评分。**

## 这个因子的公式很简单

每分钟，五档的权重为：

```text
w = [1, exp(-0.3), exp(-0.6), exp(-0.9), exp(-1.2)]
  ≈ [1, 0.741, 0.549, 0.407, 0.301]

B = Σ w_i × bid_volume_i
A = Σ w_i × ask_volume_i
I = (B − A) / (B + A + 0.00000001)

某个半小时截面的 factor = 该区间内所有有效记录的 I 的算术平均
```

靠近买一/卖一的挂单权重更大。若加权后的买盘 B=900、卖盘 A=300，则 I 约为 **0.5**；表示买方挂单相对更强，不是预测会涨 50%。半小时内持续为正，平均值也会偏正。

注意是 **先逐分钟算比值，再对比值求平均**，不是先把半小时的买卖量全部加起来，再算一次比值；两种算法一般不相等。缺失档位在这些示例中按 0 处理；全零盘口得到 0，且仍参与平均。

每个截面只需要其对应半小时内的盘口记录。因此，它本身符合你之前提出的“只依赖最近 30 分钟”方向。只是代码并不检查每个区间是否真的有 30 根：只有一条记录时也会产生均值。

## 现在可以确认的调用方式

```python
main(
    datasources={"bar1m": "当前阶段的实际数据表名"},
    start_date="开始日期时间",
    end_date="结束日期时间",
)
```

- `datasources` 是字典，因子通过 `datasources["bar1m"]` 获取行情表。开发、公榜和私榜可由平台替换，提交代码不能把行情物理表名写死。
- 代码接收的是表名和时间范围，并自行读取带真实时间戳的数据，不是一段不知道时刻的 30 分钟数组。
- 这三份示例实际返回 **`date / instrument / factor`**。之前赛事介绍写的是 `datetime / instrument / factor`，存在冲突；阅读和复现示例先遵循其 `date`，最终提交前用当前平台评测器确认。后来平台实际要求的列名就是 `date`（见 `提交须知.md`）。
- `all_instruments` 用于把股票 ID 映射成代码；`cpt_jyc_2026_instruments` 用于按 **时间 + 股票代码** 筛选当时的股票池。这两个表不是因子公式中的额外预测数据。
- `if __name__ == "__main__"` 下的日期范围和 `M.jyc_eval._latest(...)` 是示例自测入口。平台 import 后调用 `main` 时，不会执行这部分。

## 这份代码的时间表与待核对处

三个版本写的是同一张表：

| 用到的记录时间，左开右闭 | 输出时间 |
|---|---|
| (09:00, 09:30] | 09:30 |
| (09:30, 10:00] | 10:00 |
| (10:00, 10:30] | 10:30 |
| (10:30, 11:00] | 11:00 |
| (11:00, 11:30] | 11:30 |
| (13:00, 13:30] | 13:30 |
| (13:30, 14:00] | 14:00 |
| (14:00, 14:30] | 14:30 |

这是**示例源码中的时点**，尚未从评测器或真实股票池数据确认。不要凭常见交易习惯自行加上 15:00，或删掉 09:30。需要记录的差异如下：

| 发现 | 影响/处理 |
|---|---|
| 示例有 09:30，且接收 09:00—09:30 的数据；旧介绍写“跳过集合竞价” | 若分钟行情从 09:31 开始，示例不会凭空产生 09:30 分数；以真实采样表、行情覆盖和评测规则核对 |
| 示例没有 15:00，14:30 后的数据被排除 | 可能与预测窗口有关，但代码没有解释原因，不能自行推断成正式规则 |
| 旧赛事介绍写“中证 2000”，你提供的更新改为“中证 1000”，与示例注释一致 | 当前研究按中证 1000 理解；实际成员和历史生效时间仍从 `cpt_jyc_2026_instruments` 表读取 |
| SQL 第 24—26 行计算 `query_start_date = start_date − 7 天`，第 107 行查询仍使用 `start_date` | 预热变量没有生效，不能把此例当成已实现了 7 天回看，更不能据此断言私榜历史访问上限 |
| 查询从半小时中途开始时，没有为该段补足此前记录 | 例如从 10:10 开始查询，10:30 的因子可能只用到 10:10—10:30 共 21 根，与完整半小时不同 |
| SQL 注释说“按交易日聚合为日频” | 实际按 `trading_day + time_segment + instrument_id` 聚合，是日内半小时截面；注释已与实现不一致 |
| 没有重复键、整段缺失和每截面 40% 缺失率的完整验收 | 示例能算出值不等于已经通过比赛的数据质量检查 |

以上都是对示例原文件的观察；没有替官方猜测修正。

## 本地能验证到什么程度

当时写过一个本地检查脚本，用合成盘口执行未修改的 pandas 版 `main`：仅在检查进程内把两次数据读取换成固定 DataFrame，不安装假 `dai` 包，也不把本地结果当作官方平台运行。

另从 UDF 版中原样提取两个内部函数，检查盘口公式与时间边界。原始 SQL 做静态检查，没有用另一种数据库冒充 DAI 执行。

检查覆盖公式、22 个边界时刻、股票池随时间变化、乱序输入、空输入、缺失/零盘口，以及改动后续数据不影响此前截面；同时复现中途开始查询会改变首段结果。这个检查脚本依赖示例原文件，没有随仓库保留；仓库里现有的本地结构检查是 `工具/本地检查.py`。

真实数据权限、SQL 引擎行为、UDF 在 DAI 中注册、官方 `M.jyc_eval` 分数、预测效果和三小时运行限制，都需要在相应官方环境验证。
