## 一、告警是什么，为什么会出现

评测机（jyc-scorer-2.5.1）对 SQL 里出现 `bid_volume4/5`、`ask_volume4/5` 的任务会给一条 warning：

```
SQL 用到了 4–5 档盘口；本地数据只有 3 档，4–5 档为 NULL，结果与平台不同
```

这不是违规（`data_violation` 一个都没有），是**本地行情只有 3 档**这个数据限制的提示。危险在于：
本地 SQL 把 4–5 档 `COALESCE(...,0)` 成 0，所以**我们本地测到的是"1–3 档版"**，而同一个文件提交到真实平台会读全 5 档、
算出一个**我们从未测过**的信号。头部估计、与 104 的相关、换手排序都可能因此对不上。

实测（`store/platform/bar1m/202001.parquet`，399 万行）：

| 列 | 非空行数 |
|---|--:|
| `bid_volume1` / `bid_volume3` | 3,995,926 / 3,995,926 |
| **`bid_volume4` / `bid_volume5`** | **0 / 0** |
| **`ask_volume4`** | **0** |

即本地这 4 列 100% 为 NULL，`COALESCE(x,0)` 恒等于 0。

## 三、处置：修改（13 个文件全部就地改成显式 1–3 档），不取消、不重跑

改法是把 SQL 里 4–5 档的引用整个删掉，回归"全簿深度"为 1–3 档求和：

- 删除 `CAST(COALESCE(bid_volume4/5, 0) ...)`、`ask_volume4/5` 四行；
- `(bv1+bv2+bv3+bv4+bv5)` → `(bv1+bv2+bv3)`，卖出侧同理；
- 在 `sql = f"""` 前加注释说明"盘口只用 1–3 档，本地与评测机/平台一致"。

已改：**421 / 422 / 423 / 424 / 435 / 437 / 438 / 439 / 440 / 453 / 457 / 493 / 494**。
`python3 因子实验/preflight.py` 现在 0 问题、108 条提示（之前 121 条，少了这 13 条 4–5 档提示）。

**已实测验证等价**：把改前的 421（`git show 63f2206:因子代码/421_五档挂单不平衡.py`）与改后的文件在同一份本地数据上各跑一遍
（2023-01-01~01-20，本地 bar1m + instruments + exposure），输出 `date/instrument/factor` 三列**逐行完全相等、最大差 0、NaN 数相同**
（111,888 行）。另外用短窗口 smoke 把改后的 **13 个文件全部复跑通过**（日志 `/tmp/smoke_p13_{a..f}.log`、`/tmp/smoke_patch13.log`，
每个都是 `OK ... 0930zero=True`）；新写的 495/496/497/498 也已用同一套 smoke 跑通。这份检查只是防手误，改动的等价性由上面 421 的实测与 NULL 计数保证。

**为什么不取消、不重跑**：本地这 4 列恒为 NULL，删掉它们只是把"隐含的 0"写成"显式的没有"，
SQL 在本地求值**逐行完全一致**（可由上表的 NULL 计数直接推出），重跑只会得到同一个分数、白占队列。
所以已跑的 10 个任务结果继续有效，493 保持排队。

**为什么还是要改文件**：交付的是 `.py`。原文件带到平台上会多算 4–5 档，得到的不是一个我们测过的因子；
改成 1–3 档后，平台结果与本地测量同口径，公榜估计才可信。对纯盘口轴（421/422/453/437/438）这个差别是实质性的
（深度总量直接变），对头部叠加（435/457/493/494）权重小、影响小，但同样按一致口径处理。

**保留可选**：如果哪天想试"真·全五档"版本（信息更多、但本地测不了），取 `git show 63f2206:因子代码/<文件>` 就是改动前的原版。
