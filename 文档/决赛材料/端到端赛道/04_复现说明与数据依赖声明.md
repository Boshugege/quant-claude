4. **「可复现」的准确含义**：同一份代码、同一组写死的配置、同一组种子，从零训练能得到同一种模型；**不能**得到逐位相同的权重。原因有五条：成员分在不同机器和 torch 版本上训练、本地用重建标签而平台读官方标签、GPU 算子非确定性、标准化统计量各自抽样、窗口盘口通道在冻结权重里恒为 0 而平台重训时可能有值（第三节 3.8、第十节 10.3）。同配方换机器的差约 IC 0.001～0.002（来源：`e2e/reports/15_输入设计与测试流程.md`「第二台训练机：4090」）。

### 2.2 推理入口：notebook 的 `main(datasources, start_date, end_date)`

冻结 notebook 只有两个单元：一段 markdown 说明，加一个代码单元。代码单元从训练脚本导入 8 个名字，再定义 `main`（本次核对 notebook 内容）：

```python
from Transformer_modelsave_train import (
    MODEL_PATH, load_model, configure_from_ckpt, build_models, load_stats, pool, pick_device, predict_range,
)

def main(datasources, start_date, end_date):
    table = datasources["bar1m"]
    device = pick_device()
    ckpt = load_model(MODEL_PATH, map_location="cpu")
    configure_from_ckpt(ckpt)
    models = build_models(ckpt, device)
    stats = load_stats(ckpt)
    instruments = pool(start_date, end_date)
    pred = predict_range(models, table, start_date, end_date, instruments, stats, device, norm=ckpt["norm"])
    # 与 cpt_jyc_2026_instruments 内连接，去 inf／NaN／重复，按 date、instrument 排序，输出三列
```

（上面是节选，省略了日志与文件存在性检查。）

推理的完整步骤：

| 步骤 | 函数（冻结训练脚本行号） | 做什么 |
|---|---|---|
| 1 | `pick_device`（155） | 优先 CUDA，其次 MPS，最后 CPU |
| 2 | `load_model`（1014） | 读文本 JSON，把每个张量的 `{dtype, shape, data}` 还原成 torch 张量；不依赖 pickle |
| 3 | `configure_from_ckpt`（1038） | 按 JSON 恢复全局配置：字段集合 `base`、`ARCH = e04`、`E04_NORM = rel2`、`SEQ_LEN = 64`、`OUT_NEUTRAL = 1.0`、`ZERO_0930 = True`、`WIN_GROUPS = shape,book,tod`、`E04_CFG`、树成员 `GBDT_CK`；最后断言窗口通道数与结构一致 |
| 4 | `build_models`（1024） | 按 `member_cfgs` 逐个重建 6 个 `E04Net`（成员 4、5 用 GRU 编码器）并载入权重 |
| 5 | `load_stats`（1068） | 取出 6 组标准化统计量 |
| 6 | `pool`（415） | 区间内 `cpt_jyc_2026_instruments` 出现过的全部股票 |
| 7 | `predict_range`（974）→ `e04_predict_range`（2776） | 按自然月分片切窗；6 个神经网络成员逐截面前向，各取融合头输出、截面百分位排名 − 0.5，取平均；树成员用自己的字段集合第二遍构建 1055 个平铺特征、分箱、800 棵树求和、截面排名 − 0.5；按 `(6 × 神经网络平均 + 1 × 树) / 7` 合成；对 4 个行情风格特征做 1.0 倍逐截面中性化；09:30 截面输出常数 0 |
| 8 | notebook 末段 | 与 `cpt_jyc_2026_instruments` 内连接，替换 inf 为 NaN 后去掉，去重，输出 `date / instrument / factor` |

- 合成公式在 `e04_predict_range` 末段：`out["factor"] = (n_m * out["factor"] + w * rg) / (n_m + w)`，其中 `n_m = len(models) = 6`、`w = GBDT_CK["cfg"]["weight"] = 1.0`（冻结脚本第 2790–2797 行附近，本次核对）。
- 推理需要的历史：1 分钟 bar 向前多取 7 个自然日（`E04_BUFFER_DAYS = 7`，第 1285 行），30 分钟窗口表向前 130 个自然日（`WIN_LOOKBACK_DAYS = 130`，第 1284 行），盘口窗口表与收盘竞价表向前 `max(45, 20 × 1.6 + 20) = 52` 个自然日（`BOOK_LOOKBACK_DAYS = 45`，第 1333 行；取数逻辑在 `e04_iter_chunks`，第 1842 行起）。都在平台准备的约 1 年历史之内（R9）。
- 输出列名用 `factor`：与官方 demo 一致，`verify_package.py` 也断言 `list(out.columns) == ["date", "instrument", "factor"]`（来源：`e2e/scripts/verify_package.py`）。

## 三、从零训练：冻结权重是怎样产生的，怎样再做一遍

### 3.1 总览：三批训练、两台机器、一次合并

平台私榜重训是「一个进程里顺序训练 6 个成员 + 树」。我们交付的权重却是**分三批、在两台机器上**训练出来再拼起来的：macstudio 内存大但慢，4090 快约 3.9 倍但只有 64 GB 内存（来源：`e2e/reports/15_输入设计与测试流程.md`「第二台训练机：4090（10-25 晚）」）。为了让「分开训练、拼起来」与「平台一次训完」在配方上等价，我们做了三件事：

1. 本地训练入口 `e2e/scripts/train_local.py` 不另写训练逻辑，而是直接调用交付脚本的 `train_and_save`，只覆盖模块常量、换成本地数据后端 `FeatherBackend`、挂上逐轮验证的回调（来源：`train_local.py` 文件头「训练逻辑与平台私榜重训完全同一份代码」）。
2. 每个成员单独训练时用 `--n-models 1 --seed 42+k`，合并脚本 `merge_members.py` 断言第 k 个成员的种子必须是 `SEED + k`、训练区间必须相同、除 `seq_enc` 外结构必须相同，这样合并后的包与「`N_MODELS = 6`、`SEED = 42` 一次训完」在种子分配上一一对应（来源：`e2e/scripts/merge_members.py` 文件头与断言）。
3. GRU 成员在合并时被记进 `gru_members = [4, 5]`，打包时写成 `E04_GRU_MEMBERS = [4, 5]`，让平台重训按同样的分工训练（来源：`e2e/提交/提交记录.md`「E20、E21」表下说明）。

### 3.4 树成员的训练

- 入口：`e2e/scripts/e17_add_gbdt.py <E16 合并 run 目录> <输出 run 目录> '<E04_GBDT json>'`，打包脚本 `e2e/scripts/e17b_pack.sh`（来源：两个文件头；`文档/复现与消融指南.md` 3.2 表）。

- 这几项配置与 E21 冻结常量相同（`cs_rank`、0.5、2、`proxy_ind`、30、120、2020–2024、`shape,book,tod`，见 2.4 节），所以平台重训时 `gbdt_train` 用的是同一个目标。

- 算法：自写的 torch 直方图梯度提升，逐层生长到深度 8；每个特征按 400,000 个抽样的分位点分成 64 箱（0 号箱留给缺失）；每棵树抽 50% 的行、70% 的特征；左右子节点都要 ≥ 1000 个样本才分裂；不依赖 LightGBM、XGBoost、sklearn（来源：冻结脚本 `_GBTrees`、`gbdt_train`，第 2533、2616 行起）。

### 3.8 为什么重训不会与冻结权重逐位相同（以及差多少）

| 原因 | 说明 | 来源 |
|---|---|---|
| 成员分批、分机器训练 | 冻结 JSON = macstudio 上的 4 个 Transformer（MPS、torch 2.14.1）+ 4090 上的 2 个 GRU（CUDA、torch 2.11.0+cu128）+ macstudio 上更早训练的树；平台是一个进程里顺序训练 | 3.1、3.2 节 |
| 标签来源不同 | 本地训练读 `FeatherBackend.labels`，优先用由 1 分钟数据重建的 `labels_y_off.parquet`（与官方截面秩相关约 0.97）；平台走 `DaiBackend.labels`，直接查官方 `cpt_jyc_2026_vwap.vwap_return` | `e2e/交接文档.md` §3.2；冻结脚本第 181 行 |
| GPU 非确定性 | 代码没有打开 `torch.use_deterministic_algorithms` 或 cudnn 确定性开关（本次在冻结脚本中 grep 无结果）；重载自检本身就有 1e-3～3e-3 的设备差 | 3.2 节「重载最大差」 |
| 标准化统计量 | 各自在训练集上抽 200,000 个样本计算；合并时统一用成员 0 的统计量，平台重训时 6 个成员共用一份 | `merge_members.py`；冻结脚本 `e04_build_dataset` |

**差多少**：同一配方在 4090 上复跑（X22a）与 macstudio 上的原版（R22a）相比，IC 2023 −0.0007、2024 −0.0022，报告结论是「同配方换机器（torch 版本、CUDA 与 MPS）的差约 0.001～0.002，单臂差异小于这个量级的不算结论」（来源：`e2e/reports/15_…`「第二台训练机：4090（10-25 晚）」R39c／d／e 表下）。这与单种子噪声（IC 的单种子标准差 σ = 0.0013，来源：同报告「八、历史结论的种子噪声复核」）在同一量级。窗口盘口通道从 0 变成有值会带来多大差别：没有做过实验，未记录。

### 4.3 「一份脚本、两种后端」

```text
                       ┌──────────── 平台 ────────────┐
Transformer_modelsave_ │ DaiBackend(datasources["bar1m"]) │──► dai.query（平台表 + 三段 SQL）

                       │ DaiBackend + 模拟 dai           │──► DuckDB 原样执行三段平台 SQL（verify_package）
                       ├──────────── 截断检测 ─────────┤
                       │ CutBackend（继承 FeatherBackend）│──► 只返回截断时刻及之前的数据（leak_check）
                       └─────────────────────────────────┘
```

- 平台上 `train_and_save` 不传 `backend`，默认 `DaiBackend`（冻结脚本第 1189 行）。
- 本地训练由 `train_local.py` 传入 `FeatherBackend` 与两个只在本地使用的回调（`on_epoch_end` 逐轮验证、`on_data_ready`），平台上这两个回调为空（来源：`train_local.py` 文件头；冻结脚本 `train_and_save` 文档串）。
- 本地后端负责把本地文件转成平台口径：价格、成交额从「分」换成「元」；开高低收缺失由 −1 改为 NaN；用伪代码 `ID0001` 代替股票代码；本地只有 3 档盘口；本地没有 `pre_close`，用前一交易日收盘与复权因子推算（来源：`e2e/交接文档.md` §3.1；`e2e/src/feather_data.py` 文件头）。
- 平台 SQL 与本地缓存的一致性核对：30 分钟窗口 SQL 用 DuckDB 0.9.2 在本地 1 分钟数据上执行，修复 09:30 缺陷后与本地 30 分钟窗口表末价、成交额 100% 一致（来源：`e2e/reports/12_官方标签与09点30缺陷.md` §三；`e2e/scripts/sql_win30_check.py`）；盘口窗口缓存与平台 SQL 逐行核对最大差 1e-7（来源：`e2e/reports/14_E07训练记录.md` S7）。

## 八、训练与推理分离

### 8.1 文件层面

- **训练**只在 `Transformer_modelsave_train.py` 里：`__main__` 调 `train_and_save`，写出 JSON。
- **推理**只在 notebook 里：唯一的代码单元从训练脚本导入 8 个名字（`MODEL_PATH, load_model, configure_from_ckpt, build_models, load_stats, pool, pick_device, predict_range` 中除 `MODEL_PATH` 外都是函数），定义 `main`，**不调用任何训练函数**。
- 两者之间只通过 `transformer_model.json` 传递：权重、标准化统计量、树、成员结构、字段集合、回看长度、中性化力度、09:30 置零开关等全部写在 JSON 里，推理时由 `configure_from_ckpt` 恢复（来源：冻结脚本第 1038 行起）。
- `package.py` 打包时只保留 notebook 的前两个单元（`nb["cells"] = nb["cells"][:2]`，第 100 行），开发期间的试验单元不会进交付；`verify_package.py` 断言 notebook 只有 2 个单元。

### 8.2 代码路径层面：哪些东西只在训练时出现

| 组件 | 只在训练时 | 依据（冻结脚本） |
|---|---|---|
| 官方标签 `cpt_jyc_2026_vwap.vwap_return` | ✓ | `e04_iter_chunks` 第 1848 行 `if with_label:` 才调 `backend.labels`；推理调用时 `with_label=False`（`e04_predict_range` 第 2782 行） |
| 多任务目标（之后 30 分钟已实现波动、量能变化） | ✓ | 第 1864 行 `mtl = with_label and E04_MTL_W > 0` |
| 多周期辅助目标（同日之后 2 个截面的标签） | ✓ | `aux_target`，只在 `e04_train_and_save` 里对 `y` 使用 |
| 训练剔除（行情代理 + 伪行业残差） | ✓ | `proxy_table`、`neutral_matrix` 只在 `e04_train_and_save` 与 `gbdt_train` 里调用；注释「推理不需要这些特征」（第 1291 行附近） |

### 8.3 推理没有跨截面状态

- 每个截面单独前向：`e04_predict_array` 按截面分段（`_segments`）逐段计算，同伴注意力和截面排名只在同一截面内进行；合成、中性化、09:30 置零也都只用当前截面的数据（来源：冻结脚本第 2214 行起、第 2776 行起）。
- 推理不读模型自己对之前截面的输出，满足规则 R3（来源：`e2e/reports/04_…` 规则表 R3）。2026-10-10 规则明确后，早期为降换手写的输出 EMA 平滑代码已删除（来源：`e2e/reports/12_官方标签与09点30缺陷.md` §五）。
- 腿换手损失虽然在训练时把同日相邻两个截面配成一对，但它只改变训练出来的权重；推理时每个截面仍独立预测（来源：`文档/复现与消融指南.md` 3.3「推理不使用模型之前的输出；腿换手损失只在训练时作用」）。

### 8.4 训练与推理共用的部分（为什么要共用）

切窗、数值变换、标准化、模型结构、平台 SQL 都在同一个文件里，训练与推理调用同一批函数。这样训练时看到的输入与推理时看到的输入由同一段代码生成，避免「训练一套、推理一套」带来的口径偏差。历史上真出过这类问题：2026-10-11 发现因子赛道沿用的 30 分钟窗口 SQL 在 09:30 截面取不到末价（平台 1 分钟数据在 09:25 竞价之后直接是 09:31），端到端 E04 包在平台推理时 09:30 输入与本地训练不一致；修复后模拟 dai 改为用 DuckDB 原样执行平台 SQL，这个缺陷才被校验覆盖（来源：`e2e/reports/12_官方标签与09点30缺陷.md` §三）。

## 九、截断泄漏检测

### 9.1 原理

同一个打包模型做两次预测（来源：`e2e/scripts/leak_check.py` 文件头，87 行）：

1. 用全量数据预测起始日到最后一个截断日的全部截面；
2. 对每个截断时刻 c，换成「截断后端」`CutBackend` 再预测一次：1 分钟 bar、30 分钟窗口表、盘口窗口表只保留时间 ≤ c 的行，收盘集合竞价表只保留 c 所在交易日之前的交易日（竞价 15:00 才有），同时打补丁截断底层的 `feather_data.read_range`；
3. 比较 c 及之前的全部截面，差值 > 1e-6 的行数必须为 0；
4. 推理路径原样运行：6 个神经网络成员 + 树成员 + 输出中性化 + 09:30 置零。

如果模型在任何环节（特征、同伴向量、风格特征、树的平铺特征、中性化）用到了 c 之后的数据，截断前后的预测就会不同。

### 9.2 命令

```bash
python e2e/scripts/leak_check.py "e2e/提交/E21_E18g加两个GRU成员_2020-24" 2024-03-04 "2024-03-06 10:30:00" "2024-03-06 14:30:00"
```

（来源：`e2e/scripts/e21_pack.sh` 最后一行；`文档/复现与消融指南.md` 3.3。需要本地 1 分钟数据与盘口、竞价缓存，在 macstudio 上运行。）

输出格式：每个截断点一行「截断 <c>：行 <全量行数>／<截断行数>，合并 {...}，最大绝对差 …，差>1e-6 的行 …；截断时刻本身的截面 … 最大差 …」，最后一行「结论：CLEAN（截断时刻及之前的预测与全量逐位一致，未用未来数据）」或「有差异 N 行，需排查」。

### 9.6 这项检测覆盖不到的地方

1. **只覆盖少数截断点**：两到三个截断时刻、一个月左右的数据，不是全区间逐截面检测。
2. **用的是本地数据后端**：`CutBackend` 继承 `FeatherBackend`，检测的是「本地后端 + 交付推理代码」；平台 `DaiBackend` 的三段 SQL 本身由模拟 dai 在 `verify_package.py` 里执行过，但没有做截断对照。
3. **导入的是开发目录里的训练脚本**：`leak_check.py` 第 12–13 行把 `e2e/submission` 加进导入路径，用的是开发版 `Transformer_modelsave_train.py`，权重从包目录的 JSON 读取。打包当时开发版与冻结脚本只差 46 个配置常量（1.4 节），而推理用到的配置由 `configure_from_ckpt` 从 JSON 恢复，所以检测的推理路径与冻结包等价（推断，依据 1.4 节对照与 `configure_from_ckpt` 代码）。
4. **检测的是特征时点，不是训练区间**：训练区间写死在 2020–2024，公榜测试期不在这 5 年内（来源：`e2e/交接文档.md` §1.3）；私榜区间未记录。
5. **因子赛道交付物的截断检测**由因子赛道另行说明，与本节无关。

### 10.3 本次核对发现：窗口盘口通道在冻结权重里恒为 0

**现象**（2026-11-11 本次用 python 只读冻结 JSON）：

1. `stats` 的第 3–6 组（日内、日线 token 的均值与标准差，各 19 个数）里，第 7、8、9、10 位全是 NaN，其余位置正常。第 7–10 位正是 `book` 组的 4 个通道（`b_imb` 挂单量不平衡、`b_spr` 相对价差、`b_conc` 一档集中度、`b_oimb` 委托笔数不平衡）。1 分钟输入的 2 组统计量没有 NaN。
2. 标准化是 (x − 均值) ÷ 标准差，再把 NaN／inf 置 0（冻结脚本 `_std_into`、`standardize`），所以这 4 个通道无论原始值是多少，进网络时都是 0——训练和推理都一样。
3. 佐证：6 个成员的日内、日线输入投影矩阵 `p_i.weight`、`p_d.weight`（64 × 19）在这 4 列上的最大绝对值都在 0.2267–0.2294 之间，不超过 1/√19 ≈ 0.2294（PyTorch 线性层默认初始化的上界）；其余 15 列的最大绝对值是 0.47–0.95。输入恒为 0 时这 4 列权重收不到梯度，正好对得上。
4. 树成员同样：`gbdt.edges` 的 1055 行里有 167 行全为 0（训练时抽样的 400,000 个样本里这一列全是缺失或全是同一个值才会这样）。按 `_gb_flatten` 的拼接顺序映射，其中 150 个是 `book`、`book2`、`book3` 的窗口特征（这三组共 10 个通道，都来自同一张盘口窗口表，10 × (日内 9 + 日线 6) 种池化 = 150），另外 15 个是时段 one-hot 的 09:30 位（训练样本里恒为 0，1 × 15 种池化），2 个是恒为 0 的平凡特征（映射结果见 `02_最终模型E21详解.md` 第 441 行与「7.7 167 个"死特征"」；本次只核对了 167 这个总数与上述算术）。
5. 时间范围：本次读了几个相邻交付包的 `stats[2]`——E15、P16 的第 7–10 位正常；E16、P17、E18g、E21 都是 NaN。即问题出现在 P16（2026-10-23 打包）之后、E16（2026-10-24 打包）的训练数据里，此后在 macstudio 与 4090 上新建的训练集都是这样。

**原因**：仓库记录里查不到（未记录）。合并脚本比对统计量时用的是 `equal_nan=True`（`merge_members.py`），说明当时 NaN 没有被识别成通道失效。

**对复现与声明的影响**：

- **冻结模型的推理不受影响**：神经网络这 4 列恒为 0；树从未在这些特征上分裂（训练时它们全在同一个缺失箱里，而分裂要求左右两边都 ≥ 1000 个样本），所以平台上即使盘口表有值，冻结模型的输出也不变（推断，依据冻结脚本 `_gb_binize`、`_GBTrees`）。截断检测与公榜、私榜成绩都是在这个状态下得到的。
- **数据声明要收窄**：最终模型的神经网络成员实际上没有用到「窗口内 1 分钟盘口均值」，它们的盘口信息只来自 1 分钟层面的买一价、卖一价、买一量、卖一量；树成员的盘口信息只来自 1 分钟层面的 1–3 档价量与委托笔数。
- **私榜重训会不一样**：平台上 `_BOOK30_SQL` 应能取到数（间接证据：模拟 dai 用 DuckDB 执行同一段 SQL 与本地缓存逐行一致，`e2e/reports/14_E07训练记录.md` S7；早期 P04 在平台推理时用上盘口通道后公榜五项全好，`e2e/提交/提交记录.md` P04 行）。若如此，重训出的模型会真正用到这 4 个通道，与冻结 JSON 在输入上不完全一致（推断）。
- **影响范围**：这一点不涉及未来信息，也不影响冻结模型的成绩，但影响「模型看到了什么」的描述和重训的一致性。

- **内部规则的变化**：2026-10-15 我们自定的输入合规表把「因子赛道设计并验证过的预测公式（聪明钱、量价同向、大单方向、零收益占比、领先滞后、季节性均值等）」归为「灰色：不用」，自查时写明 `lead` 属于灰色、`slot` 偏灰（来源：`e2e/reports/15_…`「一、合规边界」）。2026-10-25 树成员 G8 起启用全部 12 组通道（含 `lead`），E17b、E18g、E21 的树都是这个配置（来源：`e2e/reports/15_…`「G8／G9」；1.5 节树内容哈希）。这是团队自定规则的变化：树成员只做通用池化、不加人工组合公式，每个通道仍是「原始字段在某个时间粒度上的简单聚合或截面比较」；`lead` 的选题来自因子赛道的研究方向。
- **因子赛道也借鉴过端到端的经验**，见 `文档/交接与规则/因子挖掘_来自端到端的经验.md`（属于因子赛道的材料）。

**不能使用的说法**：「端到端不含任何因子赛道的内容」「两个赛道毫无交集」。准确的说法是：**输出与因子值隔离，思路与部分通道定义有借鉴**。

### 10.7 标签口径

- **官方定义**（2026-10-11 用平台导出的两段标签表逐行核实，100% 吻合、误差小于 1e-7）：`vwap_return = end_price / vwap − 1`，窗口是截面之后的 30 分钟 (t, t+30]；`end_price` 是窗口最后一分钟的收盘价；11:30 截面对应 13:00–13:30（跳过午休）；14:30 截面对应 14:30–15:00，同一交易日、有标签（来源：`e2e/交接文档.md` §3.2；`e2e/reports/12_官方标签与09点30缺陷.md` §一）。

### 11.4 不重训就能做的只读分析（建议，均未做）

在冻结 JSON 上可以离线做、而不改动冻结文件的分析：
