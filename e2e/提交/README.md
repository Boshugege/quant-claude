# 端到端交付包

端到端赛道交给团队成员上传比赛平台的全部版本。**已交付的版本不修改，任何改动都发新编号。**

## 两类目录

| 前缀 | 数量 | 含义 |
|---|---|---|
| `E<编号>_<说明>/` | 24 个（E01–E22，含 E07b、E14b、E17b、E18g；没有 E06、E19） | 正式交付包，通常用 2020–2024 全量训练、多个成员集成 |
| `P<编号>_探针_<说明>/` | 20 个（P01–P13、P16–P19、P21–P23） | 公榜探针：通常是只训练到 2022 年的单模型（fold-A，种子 42），成对提交，用来在同一公榜页面上读出某一项改动的效果 |

不是每个包都上传过。例如 E14、E14b 打包后没有交付，E20、E22 的公榜分没有记录。以 `提交记录.md` 为准。

## 三个固定文件名

平台要求三个文件平铺上传，文件名不能改（notebook 按文件名导入训练脚本）：

```
Transformer_modelsave_train.py        训练脚本和全部共享定义；私榜阶段平台调用 train_and_save 从零重训
Transformer_modelsave_predict.ipynb   推理 notebook；平台调用 main(datasources, start_date, end_date)
transformer_model.json                权重和全部推理配置（文本 JSON，平台上限 50 MB）
```

文件名和接口沿用主办方示例的规定，内容由参赛团队编写。

## 权重只保留了 E21

公开仓库里只有最终作品 `E21_E18g加两个GRU成员_2020-24/` 带 `transformer_model.json`（约 30 MB），并保留同内容的 `E21_E18g加两个GRU成员_2020-24.zip`。其余 43 个目录只有训练脚本和推理 notebook。

原因是体积：其余权重合计有数百 MB，而它们不是最终作品。每个包的训练脚本里写死了当时的全部配置（训练区间、种子、成员数、损失权重等），配合 `提交记录.md` 和 `e2e/过程记录/` 里的训练配置，可以重新训练出统计上等价的模型，但不能逐位复现。

## 怎样重新打包

打包脚本把一次训练的产物和 `e2e/submission/` 里的训练脚本合成一个交付包：

```bash
python3 e2e/scripts/package.py <run 目录，含 transformer_model.json 与 config.json> <包名，如 E23_简述>
```

- 它把训练脚本里的配置常量改写成与权重 JSON 一致的值，并生成同名 zip（zip 被 `.gitignore` 忽略）。
- 目标目录已存在时脚本拒绝运行，所以不会覆盖已交付的包；重新打包要用新的包名。
- 多成员的包先用 `e2e/scripts/merge_members.py` 合并各成员；E21 的完整流程在 `e2e/scripts/e21_pack.sh`（其中从远端取文件的几行已不能执行）。
- 校验：`e2e/scripts/verify_package.py <交付目录>`（配置一致性、极小规模重训、跑一个月推理）和 `e2e/scripts/leak_check.py`（截断检测）。两者都需要 1 分钟行情，公开前的清理之后没有重新运行过。
- `e2e/submission/` 里的训练脚本在 E21 之后还有改动，与 E21 包内的那份不同。

## 提交记录

`提交记录.md` 是端到端赛道的分数登记：每个版本的日期、训练区间、主要配置、本地验证、公榜五项和结论，以及若干同一时刻的公榜快照。它是比赛过程中逐步追加的，前面的内容不随后来的结果改写。最终成绩和已知缺陷见仓库根目录的 `FINALS.md`。
